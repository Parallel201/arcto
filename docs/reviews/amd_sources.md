# ARCTO on AMD — source-grounded optimization reference (gfx90a / gfx942 / gfx1100)

Scope: AMD-published performance guidance + literature on GPU compression-kernel optimization, filtered for ARCTO's rule
("algorithms fixed; only launch geometry, wave size, LDS layout, registers/occupancy, coalescing/vector loads, cache
behaviour, wave primitives, atomics, sync, compile flags may change"). Every fact carries a URL. Items I could not open
or verify are marked **unverified**. Local copies of the primary PDFs/HTML used for quotes are in
`scratchpad/pdfs/*.txt` (cdna3_wp, cdna2_wp, mi300_isa, mi200_isa, rdna1_wp, AMDGPUUsage, olcf_*, advanced_hip_robey, …).

`rocm.blogs.amd.com` / `rocm.docs.amd.com` pages were not fetched because a session limit hit (they are cited "not

four 64 B L1 lines on MI2xx; a wave64 `dwordx4` load touches 1 KiB = exactly eight 128 B lines (nod-ai guide: "up to 4
adjacent global_load_dwordx4 … forms a clause that translates to a single data fabric transaction" — secondary source
[NOD]). AMD's own HIP docs: "the hardware can combine all 64 thread requests into as few as 4-8 cache line requests"
[HIP-HW]. On MI300X the L2 write path is half-line (64 B), so partially-written 128 B lines are not penalised at the
channel level [CDNA3-WP p.9].

## 2. AMD's recommended practices, mapped to ARCTO kernels

Each line: AMD statement (URL) → how it applies to LZ4 / Snappy / Cascaded (RLE+Delta+BitPack) / zfp.

1. **Coalescing for 64-lane waves.** "When consecutive threads in a warp access consecutive memory addresses, the hardware combines these into a single wide transaction" [HIP-PG]; "the hardware can combine all 64 thread requests into as few as 4-8 cache line requests" [HIP-HW]; "As stride increases … effective bandwidth drops" [HIP-PERF]. → LZ4/Snappy decompressors ported from 32-lane designs often have half the wave idle or striding per-lane over literal bytes; re-map lane→byte so 64 consecutive lanes touch 64 consecutive bytes (or 16 B/lane) when copying literals/matches into output; Cascaded/zfp streaming loads should be lane-contiguous.
2. **16-byte vector loads/stores.** "Use naturally aligned types … float4 (16-byte aligned)" [HIP-PG]; MI300 tuning guide: "Ensure global_load_dwordx4 is used in the ISA, especially when the global memory load happens in the loop" and "LDS load and store should use _b128" [MI300-TUNE]. → zfp block gather (4^d values) and Cascaded bit-pack/unpack inner loops are the obvious dwordx4 candidates; LZ4/Snappy literal copies ≥16 B can use `uint4`/`__builtin_memcpy` with 16 B alignment fallbacks.
3. **LDS bank conflicts: 32 banks × 4 B, pad or swizzle.** "Padding arrays by one element shifts addresses to avoid systematic conflicts … `__shared__ float data[32][33]`" [HIP-PG]; "prefer a struct of arrays or add padding" [RDNA-PG]; "accesses to that bank must be serialized, reducing effective LDS throughput by an integer factor … hardware can often broadcast" [HIP-PERF]; AMD's CK-Tile post shows padding vs XOR-swizzle [LDS-BLOG, not fetched]. → zfp's 4×4×4 block transposes and Cascaded's tile scans in LDS: keep row stride ≠ multiple of 32 dwords; LZ4/Snappy hash tables in LDS: spread bucket index bits so a wave's 64 probes do not collide; MI2xx/MI300 service a wave64 LDS op "over four cycles in waterfall" [ISA200/ISA300] so conflicts are counted per 16-lane group, not per 64.
4. **Divergence / EXEC.** "When threads in a warp take different execution paths, the hardware serializes both branches" [HIP-PG]; "Divergence forces EXEC to toggle individual bits" [HIP-PERF]. → token-parsing loops in LZ4/Snappy are inherently divergent; minimise by giving each wave one chunk and by doing warp-uniform decisions with `__ballot`/`readfirstlane` (see 7); keep the rare paths (long literal lengths, offset overflow) out of the hot loop.
5. **Occupancy knobs: `__launch_bounds__` and `amdgpu_waves_per_eu`.** HIP: second arg is `MIN_WARPS_PER_EXECUTION_UNIT`, not blocks/SM [HIP-CPP][HIP-PORT]; LLVM: `amdgpu-waves-per-eu` is "an optimization hint … the backend may not be able to satisfy the request" and `amdgpu-flat-work-group-size` default "1,1024" [LLVM-USAGE]; Clang: `amdgpu_num_vgpr`/`amdgpu_num_sgpr` "are deprecated. Use the amdgpu_waves_per_eu attribute" [CLANG-ATTR]; nod-ai: in HIP "to utilize more than the default maximum number of registers (128) you need to specify … `__launch_bounds__`" [NOD]; lab-notes: with launch bounds "Occupancy dropped from 4 to 2 … yet performance improved" because scratch spills vanished [LAP3]; Robey: "Default is 1024. 256 or 512 are generally the options to try for high scratch kernels" [OLCF-RP]. → Compressors (LZ4/Snappy hashing, zfp encode) are register-heavy: set `__launch_bounds__(blockDim)` truthfully and sweep `waves_per_eu` 2..4 while watching `VGPRs Spill`; decompressors (memory-bound) should aim for the ≤96-VGPR/5-wave or ≤64/8-wave rungs of the table in §1.
6. **Register-pressure hygiene.** Lab-notes rules: launch_bounds, "Move variable definition close to first use", "Avoid stack allocation", "Avoid large kernel arguments", "Minimize math function invocations", "Control loop unrolling", "Manually spill to LDS" [REGP]; check `-Rpass-analysis=kernel-resource-usage` and `--save-temps` `.vgpr_spill_count` [REGP][ISA-BLOG]; "device functions are currently always inlined and may increase register pressure" [OLCF-RP]. → nvCOMP-derived kernels carry big per-thread state arrays (zfp's 64-value block, Cascaded's per-thread element tuples); use `#pragma unroll` bounds and `__restrict__` (Robey: "Try adding restrict to more arguments" [ROBEY]).
7. **Wave-level primitives on wave64.** `__ballot`/`__activemask` "have a 64-bit return value" [HIP-CPP]; shifting lane masks with 32-bit ints is a porting bug ("use 1ull … lane_mask_t") [HIP-PORT]; `warpSize` is not a compile-time constant ("Starting with ROCm 7.0, it is early folded") [HIP-CPP]; shuffles map to `ds_bpermute` (LDS crossbar, "requires s_waitcnt, but offers low latency") while DPP row ops run "at full instruction rate" [XLANE]; `__builtin_amdgcn_ds_bpermute`, `__builtin_amdgcn_readfirstlane` exist as Clang builtins [XLANE, LLVM reviews]. → LZ4/Snappy prefix sums over token lengths and Cascaded RLE scans: use `__shfl_up/xor` with `width=warpSize` (64) or rocPRIM `warp_scan`/`hipcub::WarpScan` with logical warps; broadcast uniform values with `__builtin_amdgcn_readfirstlane` to move them into SGPRs.
8. **hipCUB/rocPRIM vs hand-rolled.** hipCUB is "a thin, header-only wrapper library for rocPRIM" [HIPCUB]; rocPRIM warp ops run on "logical warps" of `VirtualWaveSize ≤ hardware warp` (64) [ROCPRIM-SCAN]. → prefer `hipcub::BlockScan/WarpScan` for the Cascaded/RLE offsets and zfp/bitpack prefix sums; the `ARCH`/logical-warp template parameters must be 64-aware or the scan silently uses only 32 lanes.
9. **Non-temporal loads/stores.** `__builtin_nontemporal_store` "allows store operations to bypass L2 cache, freeing cache capacity for frequently-reused data" — 1.19× on MI250X from a one-line change [LAP3]; ISA semantics: SLC streaming (MI2xx) / NT=1 "Hit Stream … Hit Evict" (MI300) [ISA200][ISA300]; known lowering bug for float types [LLVM-BUG]. → decompression output and compressed-stream writes are write-once: mark them non-temporal so LZ4/Snappy dictionaries (re-read window) and zfp/Cascaded input stay in L2; verify in ISA that `nt`/`slc` actually appears.
10. **L2/LLC-aware launch geometry.** Lab-notes part 4: re-indexing blocks so a working set fits L2 raised L2 hit 33%→66% and bandwidth 555→1070 GB/s on MI250X [LAP4]; MI300X: L2 is per-XCD and workgroups are round-robined across 8 XCDs [MI300-SYSOPT]; XCD-aware remapping raised L2 hit 43%→92% [XCD-SWZ]. → on MI300X, chunks that share an LZ4/Snappy dictionary region or zfp neighbouring blocks should be mapped to the same XCD via `blockIdx` swizzle (`xcd = wgid % 8`); keep the per-XCD working set < 4 MB; MALL "early spill" appears at ~128 MB [MALL].
11. **Atomics.** 32/64-bit integer and FP atomics supported on all three [HF]; `-munsafe-fp-atomics` "indicates … all floating-point atomic function calls are allowed to use an unsafe version" [HIP-CPP]; CDNA2 "boosts the throughput for FP64 atomic operations … in the L2 cache" [CDNA2-WP]. → ARCTO uses integer atomics for output offsets; avoid a global 64-bit atomic per token (hot-spot on one L2 channel) — aggregate per wave with ballot/prefix and issue one atomic per wave or per block.
12. **Occupancy is not the goal.** "Peak occupancy does not always mean peak performance" [OCC]; "High-performance kernels … often operate at low occupancy" [HIP-PERF]; Little's-law framing: "you need hundreds of independent in-flight operations" [HIP-PERF]. → decompressors should issue several independent dwordx4 loads per lane before consuming (software pipelining) rather than rely only on wave count.
13. **Workgroup size.** "Make the workgroup size a multiple of 64" [RDNA-PG]; "Choosing block sizes as multiples of 64 or 32 prevents partial warps" [HIP-PG]; "use a workgroup size of 256 (or a multiple of 256)" to fill 4 SIMDs [NOD]. → blockDim 256 with 4 waves/block is the safe default across gfx90a/gfx942; on gfx1100 compare wave32 (default) vs `-mwavefrontsize64` builds per kernel.
14. **Compile flags & checks.** `-Rpass-analysis=kernel-resource-usage` prints SGPRs/VGPRs/AGPRs/ScratchSize/Occupancy/LDS [REGP][ISA-BLOG]; `--save-temps` (+`-g`) gives ISA with `.vgpr_spill_count` [ISA-BLOG]; `-mcumode`/`-mno-cumode`, `-mwavefrontsize64` target features [LLVM-USAGE]; `-munsafe-fp-atomics` [HIP-CPP]; `--offload-arch=gfx90a,gfx942,gfx1100` (compiler reference page https://rocm.docs.amd.com/projects/llvm-project/en/latest/reference/rocmcc.html — **not fetched**). → add a CI step that diffs resource usage per kernel per arch.

## 3. Literature digest (what transfers under the "don't change the algorithm" rule)

Legend: **[kernel-level, transferable]** vs **[changes the algorithm/format — avoid]**.

1. **nvCOMP (baseline design notes).** NVIDIA, "Cascaded Compression" docs https://docs.nvidia.com/cuda/nvcomp/cascaded.html ; LZ4 docs https://docs.nvidia.com/cuda/nvcomp/lz4.html ; GTC 2020 S21597 "Software-Based Compression for Analytical Workloads" (Sakharnykh & Mueller) https://developer.nvidia.com/gtc/2020/video/s21597-vid . Cascaded: RLE via "Threads identify run starts by comparing consecutive values, then use prefix sums"; delta decode "uses exclusive prefix sum"; bit-packing via "Parallel scan/reduction finds min/max". LZ4: "each block is compressed (or decompressed) concurrently", hash table of recent bytes. → Transferable: all three are scan-dominated; on wave64 swap CUB block-scan configs for hipCUB with 64-lane logical warps and re-tune items-per-thread so a 256-thread block still covers the same tile. Nothing here forces format changes.
2. **Künas, Freytag, Bez, Araújo, Navaux, "Characterizing Lossless GPU Data Compression Across AMD CDNA and RDNA Architectures", ICCSA 2026** https://link.springer.com/chapter/10.1007/978-3-032-30491-9_23 (abstract via search). Ports LZ4/Snappy/Cascaded to HIP on MI50/MI210/MI300X/RX 7900 XT; "MI300X achieves up to 11× higher decompression throughput than the MI50, while RDNA 3 is competitive for compression workloads characterized by irregular memory accesses"; "transfers dominate end-to-end execution time". → Baseline for ARCTO; motivates GPU-resident pipelines and per-arch tuning.
3. **Sitaridi, Müller, Kaldewey, Lohman, Ross, "Massively-Parallel Lossless Data Decompression" (Gompresso), ICPP 2016** https://arxiv.org/abs/1606.00519 . Warp-per-block decoding of LZ77+Huffman; threads of a warp resolve back-references cooperatively; "the second [technique] sacrifices some compression efficiency to eliminate data dependencies" (per-warp high-water mark) — 2× vs multi-core zlib. → **[kernel-level]** warp-cooperative match copy with intra-warp round-based dependency resolution transfers to LZ4/Snappy decode (64-lane rounds on AMD). **[avoid]** high-water-mark encoding (changes the stream).
4. **Ozsoy & Swany, CULZSS (PPAC 2011)** https://web.cs.hacettepe.edu.tr/~aozsoy/papers/2011-ppac.pdf ; pipelined LZSS (ICPADS 2012) https://www.researchgate.net/publication/258234899_Pipelined_parallel_LZSS_for_streaming_data_compression_on_GPGPUs ; FGCS 2014 https://www.sciencedirect.com/science/article/abs/pii/S0167739X13001362 . Block-per-chunk LZSS with shared-memory window; pipelining of H2D/compute/D2H gave +46.65%. → **[kernel-level]** stream-overlapped batches (ARCTO host side) and LDS-resident window; **[avoid]** its LZSS token format.
5. **Zhang, Tian, Di, Yu, Swany, Tao, Cappello, "GPULZ" (ICS 2023)** https://arxiv.org/abs/2304.07342 , DOI 10.1145/3577193.3593706, code https://github.com/hpdps-group/ICS23-GPULZ . "change prefix sum from one pass to two passes and fuse multiple kernels to reduce data movement between shared memory and global memory"; "adapting data partitions to different GPU architectures to maximize shared memory utilization". → **[kernel-level]** kernel fusion of match+local-scan, arch-specific chunk size chosen to fill 64 KB LDS; **[avoid]** multi-byte-symbol matching (format change).
6. **Park et al. (NVIDIA/UIUC), "CODAG: Characterizing and Optimizing Decompression Algorithms for GPUs" (arXiv 2307.03760, 2023)** https://arxiv.org/abs/2307.03760 . "CODAG eliminates the use of specialized groups of threads … assigns compressed chunks to warps rather than thread blocks"; warp-level sync "has much lower latency and higher throughput than block-level"; reads "performed on a cache-line granularity and are thus coalesced"; 13.46×/5.69×/1.18× vs RAPIDS for RLE v1/v2/Deflate. → **[kernel-level, high value]** warp-per-chunk with no dedicated prefetch warp; on AMD that means one wave64 per chunk, `__syncthreads` replaced by wave-implicit sync, and input read in 1 KiB (64×16 B) slabs.
7. **Shavidze, "What Actually Serializes GPU LZ77 Decode" (arXiv 2608.10188, Aug 2026)** https://arxiv.org/abs/2608.10188 and "Compressed-Resident Genomics" (arXiv 2606.18900) https://arxiv.org/abs/2606.18900 . On H100 "parse, not copy, holds 64-72% of device-resident decode time"; bounding chain depth moves latency ≤2.8%; an uncoalesced 1-B-per-thread write against a 128-byte line has "bus efficiency 4.4% and a coalesced write of the same data is 39× faster". → **[kernel-level]** optimise token parsing (wave-wide speculative parse + ballot) before match copies; make literal/match writes lane-contiguous. **[avoid]** encoder-side absolute-offset / distance-history removal (format change).
8. **Morfiadakis, "Parallel LZ77 Decoding using a GPU" (2018)** https://hgpu.org/?p=18542 and Wesley, "Massively Parallel LZ77 Compression and Decompression on the GPU" (MSc, Texas State 2022) https://digital.library.txst.edu/items/28585afe-28a9-45a5-8658-463bfa68da26 . Negative result: in-memory synchronisation-based parallel LZ77 decode loses to serial — reinforces per-wave independent chunks rather than cross-block dependency resolution.
9. **Azami, Fallin, Burtscher, "Efficient Lossless Compression of Scientific Floating-Point Data on CPUs and GPUs" (ASPLOS 2025) + LC framework** https://userweb.cs.txstate.edu/~burtscher/papers/asplos25.pdf , DOI 10.1145/3669940.3707280, https://github.com/burtscher/LC-framework . "all stages … operate on chunks of 16 kilobytes. We choose this size so that we can fit two chunk buffers in the GPU's shared memory"; "divide each 16 kB data chunk into 32 512-byte subchunks. This enables us to efficiently process each subchunk by a warp"; RLE/zero-elimination via "block-level parallel prefix sum that utilizes warp-level primitives and shared memory", "fast CUDA shuffle operations to exchange data between the threads in a warp (without accessing memory)"; encoder/decoder "keep all data in shared memory within and between" stages. → **[kernel-level]** the Cascaded pipeline can run RLE→Delta→BitPack entirely in LDS per chunk (two 16 KB buffers fit in 64 KB), with a wave64 owning 1 KB sub-chunks; **[avoid]** LC's own transforms (different algorithm).
10. **Knorr, Thoman, Fahringer, "ndzip-gpu" (SC21)** https://dl.acm.org/doi/10.1145/3458817.3476224 , code https://github.com/celerity/ndzip (full text not fetched). "a novel, efficient warp-cooperative primitive for vertical bit packing" and "efficient memory access patterns"; one thread block per hypercube. → **[kernel-level]** warp-cooperative transposed (vertical) bit-packing is directly applicable to Cascaded BitPack and to zfp's bit-plane emission: each lane owns one bit position, `__ballot` builds a 64-bit plane word per step (wave64 yields 64-bit words natively — nvCOMP's 32-bit ballot path needs a 64-bit rewrite). Algorithm/format unchanged as long as the emitted bit order is preserved.
11. **Shanbhag, Yogatama, Yu, Madden, "Tile-based Lightweight Integer Compression in GPU" (SIGMOD 2022)** https://anilshanbhag.com/static/papers/gpufor_sigmod22.pdf , code https://github.com/anilshanbhag/gpu-compression . "each thread block collectively loads a block of encoded data into shared memory, which is called a tile. Next, multiple steps of decompression are applied on the tile directly in shared memory, avoiding multiple passes to the global memory"; decodes "at close to memory bandwidth"; 2.2×/2.6× faster than nvCOMP in decompression/query. → **[kernel-level, high value for Cascaded]** fuse RLE/Delta/BitPack decode stages per tile in LDS instead of one kernel + global round-trip per layer (ARCTO keeps nvCOMP's format; only the pass structure changes). Note their tile format differs — only the fusion idea transfers.
12. **Afroozeh, Felius, Boncz, "Accelerating GPU Data Processing using FastLanes Compression" (DaMoN 2024)** https://ir.cwi.nl/pub/34260/34260.pdf ; Hepkema et al., "G-ALP" (DaMoN 2025) https://ir.cwi.nl/pub/35205/35205.pdf . "an access granularity of decoding vectors of 1024 values is too large for a single GPU warp due to register pressure"; remedies: "dividing a vector into mini-vectors", widths beyond 32-bit, "increased the block-width from 32 to 128 or even 256"; G-ALP moves to "one-value-per-thread processing". → **[kernel-level]** choose items-per-thread for bit-unpack so a wave64 holds ≤64 VGPRs of live state (see §1 table); **[avoid]** FastLanes interleaved layouts (format change).
13. **Huang et al., cuSZp2 (SC24)** https://dl.acm.org/doi/10.1109/SC41406.2024.00021 , https://github.com/szcompressor/cuSZp (abstract via search). Single-kernel design, "optimizes memory access patterns, and hides synchronization latency" (global prefix with latency control); 332/513 GB/s on A100. → **[kernel-level]** decoupled-lookback style single-pass offsets instead of a separate scan kernel for Cascaded/LZ4 batch output offsets — on AMD, beware the 64-bit flag atomics hot-spotting one L2 channel. **[avoid]** its quantisation/encoding.
14. **Zhang et al., FZ-GPU (HPDC 2023)** https://arxiv.org/abs/2304.12557 . "warp-level optimization to avoid data conflicts for bit-wise operations in bitshuffle, maximize shared memory utilization, and eliminate unnecessary data movements by fusing different compression kernels". → **[kernel-level]** same bitshuffle/LDS fusion lessons for zfp bit-plane packing and Cascaded BitPack. **[avoid]** lossy pipeline.
15. **Rivera, Di, Tian, Yu, Tao, Cappello, "Optimizing Huffman Decoding …" (IPDPS 2022)** https://arxiv.org/abs/2201.09118 ; Weißenberger & Schmidt, "Massively Parallel Huffman Decoding on GPUs" (ICPP 2018) https://dl.acm.org/doi/10.1145/3225058.3225076 ; Yamamoto et al., gap arrays (ICPP 2020) https://dl.acm.org/doi/abs/10.1145/3404397.3404429 . Rivera: "using shared memory on decoding/writing phases, online tuning the amount of shared memory … improving memory access patterns, and reducing warp divergence" → 3.64×. → **[kernel-level]** online LDS sizing and divergence reduction are generic; ARCTO has no Huffman stage, so this is technique-only. **[avoid]** gap arrays / self-sync decoding (format).
16. **DietGPU (Meta, 2022)** https://github.com/facebookresearch/dietgpu . "The primitive unit of compression are 4 KiB segments of the input data, which are assigned to individual warps"; 250–410 GB/s ANS on A100; "not worth using … unless one has at least 512 KiB of data". → **[kernel-level]** warp-per-4 KiB granularity and the saturation rule (segments ≈ resident warps) are good sizing heuristics for ARCTO batch APIs on 304-CU MI300X. **[avoid]** ANS.
17. **zfp (LLNL).** Docs: CUDA execution policy "Only the fixed-rate mode … is supported", "zfp assigns each chunk to a thread", "Requires 64-bit word size", no HIP policy listed https://zfp.readthedocs.io/en/latest/execution.html ; releases: "0.5.4 … Added support for CUDA fixed-rate compression and decompression", 1.0.0 fixed "CUDA bit offsets are limited to 32 bits" https://github.com/LLNL/zfp/releases ; project page https://computing.llnl.gov/projects/zfp ("up to … 800 GB/s aggregate throughput on recent GPUs"). The LLNL docs I fetched list no HIP backend — ARCTO's HIP zfp port is therefore the portability reference; Lindstrom's 2014 TVCG paper ("Fixed-Rate Compressed Floating-Point Arrays", IEEE TVCG 20(12)) is the algorithm source (title from search; not fetched). → **[kernel-level]** one-thread-per-block-of-4^d is register-heavy (64 values live) — the ASPLOS/ndzip wave-cooperative bit-plane emission is the main AMD lever; 64-bit word streams match wave64 ballots. **[avoid]** variable-rate index formats not in the nvCOMP-2.2 zfp path.
18. **MGARD-X** https://github.com/CODARcode/MGARD/blob/master/doc/MGARD-X.md , https://www.sciencedirect.com/science/article/pii/S2352711023002868 . "implemented in C++11, OpenMP, CUDA, HIP, and SYCL … compile-time auto-tuning and runtime adaptive scheduling". → Example of a HIP-portable compressor with per-backend tuned kernel templates — pattern for ARCTO's per-arch constants. Algorithm not relevant.
19. **Funasaka, Nakano, Ito, "Adaptive loss-less data compression method optimized for GPU decompression" (CCPE 2017)** https://onlinelibrary.wiley.com/doi/abs/10.1002/cpe.4283 . Designs the format for GPU decode ("1.22 to 23.5 times faster than Gompresso, CULZSS, and LZW"). → **[avoid]** (format change); only the observation that decode-side memory layout dominates is reusable.
20. **Lurati, Heldens, Sclocco, van Werkhoven, "Bringing Auto-tuning to HIP" (Euro-Par 2024, best paper)** https://arxiv.org/abs/2407.11488 , DOI 10.1007/978-3-031-69577-3_7 . "auto-tuning has a significantly higher impact on performance on AMD compared to Nvidia (10x vs 2x)"; "applications tuned for Nvidia do not perform optimally on AMD"; on MI250X/W6600 the best configs favoured "small block sizes combined with spatial tiling … to reduce register usage". → **[kernel-level]** sweep block size / items-per-thread / unroll per arch with Kernel Tuner or a custom harness; do not port CUDA constants verbatim.
21. **Choudhary et al. (AMD/Duke), "Optimizing Attention on GPUs by Exploiting GPU Architectural NUMA Effects" (arXiv 2511.02132)** https://arxiv.org/abs/2511.02132 ; SwizzlePerf https://arxiv.org/abs/2508.20258 (abstract via search). MI300X "distributes workgroups across compute dies using a chunked round-robin"; swizzle `xcd = wgid % NUM_XCD; local = wgid // NUM_XCD` raised L2 hit 43%→92%, up to 50% speedup. → **[kernel-level]** blockIdx remap for chunk batches on MI300X (no algorithm change).

## 5. Open questions / things the docs do not settle

1. **CDNA3 max waves per SIMD.** I found "8 waveslots per-SIMD" stated only for CDNA2 [RCP-PIPE]; the CDNA3 white paper and MI300 ISA text I grepped do not state the number (chips&cheese claims the SIMD tracks "8 to 24" threads — interpretation unclear). Treat 8 as working assumption; confirm with `-Rpass-analysis` (`Occupancy [waves/SIMD]`) on gfx942.
2. **RDNA3 ISA-level facts** (VGPR allocation granularity, wave64 register accounting, LDS bank phases for wave64, cache-line sizes of L0/L1/L2, `global_load_b128`) — the official PDF was not retrievable here; HIP docs, GPUOpen and the RDNA gen-1 white paper are the sources used. Re-verify against https://www.amd.com/system/files/TechDocs/rdna3-shader-instruction-set-architecture-feb-2023_0.pdf.
3. **LDS bank count on RDNA3:** HIP docs say "64 banks" for RDNA2+ [HIP-HW]; GPUOpen and chips&cheese say 32 banks per 64 KB half (2×32 per WGP). The practical rule (32-dword stride conflicts) is the same, but which lanes form a phase in wave64 mode is unverified.
4. **Whether wave64 or wave32 is better for ARCTO on gfx1100** — AMD gives no compute-specific guidance beyond "compiler decides"/two-cycle issue; must be measured per kernel (`-mwavefrontsize64`). Also CU vs WGP mode (`-mcumode`) effect on 64 KB-LDS kernels is undocumented for compute.
5. **Non-temporal lowering correctness** for non-integer types is an open LLVM bug [LLVM-BUG]; check ISA for `nt`/`slc` bits after using `__builtin_nontemporal_*`.
6. **MI300X workgroup→XCD policy** is documented only in system-optimisation/tuning material and third-party papers (round-robin, chunk=1); whether it holds under all partition modes (CPX/NPS) and driver versions is unverified — measure L2 hit per XCD.
7. **Exact L2 line/channel geometry for MI300X writes** (64 B half-line writes) vs reads (128 B) and how partial-line stores from decompressors are counted in `TCC_EA_WRREQ` is not spelled out in the profiler docs I read.
8. **zfp HIP backend upstream:** LLNL docs list serial/omp/cuda only; whether a HIP execution policy exists in a newer zfp release was not verified.
9. **Bandwidth of `ds_bpermute`-based `__shfl` vs DPP on wave64** — GPUOpen gives qualitative statements only; nod-ai quotes ~50 cycles vs 4–12 (secondary, unverified).
10. **Sources not opened:** ROCm blog posts on LDS bank conflicts (CK-Tile), MI355X occupancy math, profiling-guide parts 1–3; ACM full texts (ndzip-gpu, cuSZp2, GSST, SC25 CDNA3 papers); the Springer full text of the ICCSA 2026 ARCTO baseline paper. Their claims above are limited to abstracts/search summaries.

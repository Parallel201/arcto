### 1.2 Library target (`src/CMakeLists.txt`)

- Sources are globbed: `HIP_SOURCES = ./*.hip ./lowlevel/*.hip ./highlevel/*.hip` and `CPP_SOURCES = ./*.cpp ./lowlevel/*.cpp ./highlevel/*.cpp` (`src/CMakeLists.txt:76-83`). `.hiph` headers are never compiled directly.
- **CUDA backend language flip [verified]:** `set_source_files_properties(${HIP_SOURCES} PROPERTIES LANGUAGE CUDA)` (`:87`), guarded by `if (CUDA_BACKEND)` (`:85-88`). The `.hip` files are then fed to nvcc as CUDA; `#include <hip/hip_runtime.h>` resolves to `include/cuda_shim/hip/hip_runtime.h` (see §1.4).
- CUDA archs: `GPU_ARCHS = 60; 70-real; 75-real; 80` depending on nvcc version (`:50-63`), applied via `CUDA_ARCHITECTURES` property (`:67`). `target_compile_options(arcto PRIVATE $<$<COMPILE_LANGUAGE:HIP>:--expt-extended-lambda>)` at `:68-69` is **dead** on the CUDA backend (the sources are LANGUAGE CUDA there, and the macro is only invoked under `CUDA_BACKEND`).
- Static vs shared: `BUILD_STATIC` or MSVC → STATIC, else SHARED (`:90-99`).
- Include dirs: `PUBLIC $<BUILD_INTERFACE:src>` and `include` (`:101-102`), plus a global `include_directories(src)` (`:113`).
- Optional external codecs `bitcomp`, `gdeflate`, `ans` linked PRIVATE when found (`:115-128`); zfp linked `PRIVATE zfp::zfp` (`:134-136`).
- `BUILD_TESTS` adds three test subdirs: `test`, `highlevel/test`, `lowlevel/test` (`:138-142`). Note: `hip::hipcub` is *found* (top `:122`) but never linked to `arcto`; hipcub headers resolve only because `HIP_INCLUDE_DIRS` (`/opt/rocm/include`) happens to contain them **[verified]**.

### 1.3 Exactly which flags reach HIP device code today (AMD build)

**[verified from the CMake files]** the project itself adds only:
- `-fPIC` (twice: `CMAKE_HIP_FLAGS` `CMakeLists.txt:146` and `CMAKE_POSITION_INDEPENDENT_CODE` `:133`);
- `-D__HIP_PLATFORM_HCC__ -D__HIP_PLATFORM_AMD__` (`:126`) and one of `-DENABLE_HIP_OPT_WARPSIZE64` / `-DUSE_WARPSIZE_32` (`:128-132`);
- Debug only: `-g -ggdb` (`:160`);
- `-Wno-unused-result` on the zfp target only (`:304-305`).

**[CMake-default, verify on the host with `compile_commands.json`]** CMake's HIP language (clang driver) adds per TU: `-x hip`, one `--offload-arch=<gfx>` per entry of `CMAKE_HIP_ARCHITECTURES`, `-std=gnu++17` (from `CMAKE_HIP_STANDARD 17`), `-Darcto_EXPORTS` (shared lib), and the build-type flags. CMake's Clang-HIP module initialises `CMAKE_HIP_FLAGS_RELEASE_INIT` to `-O3 -DNDEBUG`, `_DEBUG_INIT` to `-g`, `_RELWITHDEBINFO_INIT` to `-O2 -g -DNDEBUG`, `_MINSIZEREL_INIT` to `-Os -DNDEBUG` (same `__compiler_clang` macro that serves CXX). So **Release HIP device code is compiled at `-O3` without the project saying so**, and Debug HIP device code is `-O0` (clang default when no `-O`) `-g -g -ggdb`. The explicit `-O3` at `:152` only affects CXX (and duplicates CMake's own `-O3`, harmless). Recommendation: do not rely on the implicit default — add `set(CMAKE_HIP_FLAGS_RELEASE "${CMAKE_HIP_FLAGS_RELEASE} -O3")` symmetrically or at least `message(STATUS "HIP release flags: ${CMAKE_HIP_FLAGS_RELEASE}")` so a misconfigured toolchain is visible.

**Not present anywhere in the tree [verified by grep]:** `-munsafe-fp-atomics`, `-ffast-math`, `-fgpu-rdc`, `-flto`/`-foffload-lto`, `-mcumode`/`-mno-cumode`, `-mwavefrontsize64`/`-mno-wavefrontsize64`, `-Rpass-analysis`, `--save-temps`, `-mllvm`, `hipcc`, `CMAKE_HIP_COMPILER`.

### 1.4 The HIP→CUDA shim (how HIP sources compile as CUDA)

`include/cuda_shim/hip/hip_runtime.h` (MIT, `:1-21`):
- Compiles only when `__HIP_PLATFORM_NVCC__`/`__HIP_PLATFORM_NVIDIA__` are defined (set globally by `setup_cuda_build`, `CMakeLists.txt:96`), otherwise `#error` (`:70-72`).
- `#include "cuda_runtime.h"` (`:27`) then ~40 one-to-one `#define`s mapping `hip*` runtime symbols/types/enums to `cuda*` (`:29-69`): types (`hipStream_t`, `hipEvent_t`, `hipError_t`, `hipDeviceProp_t`, `hipPointerAttribute_t`, `hipMemcpyKind`), memory (`hipMalloc/Free/MallocAsync/FreeAsync/HostMalloc/HostFree/MallocManaged/Memcpy/MemcpyAsync/Memset/MemsetAsync`), enums (`hipMemcpy*`, `hipHostMallocDefault`, `hipMemoryTypeDevice`, `hipSuccess`, `hipErrorInvalidValue`), device/stream/event APIs, `hipOccupancyMaxActiveBlocksPerMultiprocessor`, `hipPointerGetAttributes`, `hipRuntimeGetVersion`, `hipDevAttrComputeCapabilityMajor`.
- Because the shim is *only* `#define`s over `cuda_runtime.h`, kernel syntax (`<<<>>>`, `__global__`, `__shared__`, `threadIdx`, `atomicAdd`, `__shfl*`, `__ballot`) is native CUDA — the `.hip` files are valid CUDA C++ by construction. Anything not in the list (e.g. `hipDeviceGetAttribute` enums other than the one mapped, `hipHostMallocMapped`, `hipLaunchKernelGGL`) would fail to compile on the CUDA path — the list is the effective "portable HIP subset" contract.
- `include/cuda_shim/hip/hip_cooperative_groups.h:26-30` simply includes CUDA's `<cooperative_groups.h>`; `hlif_shared.hiph:53-54` does `#include <hip/hip_cooperative_groups.h>; namespace cg = cooperative_groups;` so `cg::this_thread_block()`/`cg::tiled_partition<N>` work on both.
- The shim directory is exposed globally (`CMakeLists.txt:99`) and deliberately *not* `include/arcto`, to avoid shadowing the vendored zfp's `zfp.h` (`:97-98`).
- `src/arcto_hipcub.hiph:58-63` completes the picture: AMD → `<hipcub/hipcub.hpp>`, otherwise `<cub/cub.cuh>` + `namespace hipcub = cub;`.
- ZFP execution policy flips with the same macros: `src/lowlevel/ZFPBatch.cpp:25-29` (`zfp_exec_cuda` vs `zfp_exec_hip`).

### 1.5 `CMAKE_HIP_ARCHITECTURES` / `AMDGPU_TARGETS` / `GPU_TARGETS`

- `CMAKE_HIP_ARCHITECTURES` is the single source of truth; the user passes it (README.md:60-63 shows `"gfx90a;gfx942"`). `AMDGPU_TARGETS`/`GPU_TARGETS` are forced equal (`CMakeLists.txt:109-118`) because ROCm's `hip-config.cmake`/`hipcub-config.cmake` consume them (the `hip::device` imported target, used by vendored zfp at `third_party/zfp/src/CMakeLists.txt:46`, carries `--offload-arch` for `GPU_TARGETS`). A mismatch would produce duplicate/mismatched `--offload-arch` lists — hence the FATAL_ERROR.
- Benchmarks additionally set the `HIP_ARCHITECTURES` target property from `CMAKE_HIP_ARCHITECTURES` (`benchmarks/CMakeLists.txt:75-77`), redundant but harmless.
- If unset, CMake tries to detect from the toolchain; README.md:69-70 already says to set it explicitly when no GPU is present at configure time. Multi-arch lists produce a fat binary (one device compile per arch per TU; build time scales linearly).

Important consequence **[verified]**: the wave size is a *build-time global*, not a per-`--offload-arch` property. Clang compiles gfx10/gfx11 in wave32 by default and gfx9 in wave64; ARCTO never passes `-mwavefrontsize64`, so a build with `CMAKE_HIP_ARCHITECTURES="gfx90a;gfx1100"` cannot be correct for both targets with either option value. There is also no runtime guard comparing `hipDeviceProp_t::warpSize` against the compiled constant. See §3.3.

- The header's comment says HIP's second `__launch_bounds__` argument is "min_blocks_per_cu" (`:98`). So `(1024,4)` asks for ≥4 waves/SIMD, `(512,2)` ≥2, `(512,3)` ≥3, `(256,8)` ≥8 waves/SIMD (the latter would cap VGPRs at 64 on CDNA). The values in use are mild, but the documented intent is wrong and should be re-derived per architecture (§3.6).
- `wave_reduce_sum` and `wave_scan_*` call raw `__shfl_down`/`__shfl_up` on the NVIDIA branch although the header itself (`:244-246`) explains that is why `wave_shfl_down` exists; `wave_reduce_sum` is instantiated by `RunLengthEncodeGPU.hip:110` so the CUDA backend depends on deprecated non-`_sync` shuffles there.
- `WAVEFRONT_MASK ((1ULL << WAVEFRONT_SIZE) - 1)` with `WAVEFRONT_SIZE == 64` is a shift by the full width (UB); it is only used in dead code, so harmless today.

### 2.6 HLIF architecture (high-level interface)

Public surface: `include/arcto/arctoManager.hpp` — `CompressionConfig`/`DecompressionConfig` (pimpl around a pinned `arctoStatus_t*`, `:75-136`), abstract `arctoManagerBase` (`:141-236`: `configure_compression`, `compress`, `configure_decompression(buffer|config)`, `decompress`, `set_scratch_buffer`, `get_required_scratch_buffer_size`, `get_compressed_output_size`), `PimplManager` (`:238-301`) that forwards to an `impl`; `include/arcto/arctoManagerFactory.hpp:70` `create_manager(comp_buffer, stream, device)`.

Internal layering: `ManagerBase<FormatSpecHeader>` (`src/highlevel/ManagerBase.hpp`) → `BatchManager<FormatSpecHeader>` (`BatchManager.hpp`) → `<Codec>BatchManager` (e.g. `LZ4Manager.hpp:67-157`) wrapped by the public `<Codec>Manager` pimpl (`LZ4Manager.hpp:161-175`).

**Chunking** — `BatchManager::do_configure_compression`: `num_chunks = roundUpDiv(uncompressed_size, uncomp_chunk_size)` (`BatchManager.hpp:259-262`); `calculate_max_compressed_output_size = sizeof(CommonHeader) + sizeof(FormatSpecHeader) + 8*n + 4*n + 2*4*n + max_comp_chunk_size*n` (`:213-224`). Note the size uses `sizeof(uint32_t)` for chunk sizes but the layout actually uses `size_t` for both offsets and sizes (`:245-246`, `hlif_shared_types.hpp:96-97`) — the estimate is 4 bytes/chunk short of the layout but absorbed by the alignment/over-estimate of `max_comp_chunk_size`.

**Header format** (`hlif_shared_types.hpp:68-83`, written on device by `fill_common_header`, `hlif_shared.hiph:108-125`):
`CommonHeader{ magic_number=0; major=2; minor=2; FormatType format (uint8: LZ4=0,Snappy=1,ANS=2,GDeflate=3,Cascaded=4,Bitcomp=5); uint64 comp_data_size (atomic output cursor, zeroed by hipMemsetAsync at ManagerBase.hpp:224); uint64 decomp_data_size; size_t num_chunks; bool include_chunk_starts=true; uint32 full_comp_buffer_checksum=0; uint32 decomp_buffer_checksum=0; bool per-chunk checksum flags=false; size_t uncomp_chunk_size; uint32 comp_data_offset }`, followed immediately by the codec's `FormatSpecHeader` (copied H2D from pinned host at `ManagerBase.hpp:220-222`), then — at the next `size_t`-aligned address (`roundUpToAlignment<size_t>`, `BatchManager.hpp:245`) — `size_t comp_chunk_offsets[n]`, `size_t comp_chunk_sizes[n]`, `uint32 comp_chunk_checksums[n]`, `uint32 decomp_chunk_checksums[n]` (never filled), then the gap-less compressed payload (`:248-251`). `comp_data_offset` records payload start relative to the header (`hlif_shared.hiph:124`); `get_compressed_output_size` = `comp_data_size + comp_data_offset` via a *synchronous* `hipMemcpy` (`ManagerBase.hpp:128-137`).

**Kernels launched per `compress()`** (`ManagerBase.hpp:203-228` → `BatchManager::do_compress` `:226-257`): (1) `hipMemcpyAsync` of the format header; (2) `hipMemsetAsync(comp_data_size)`; (3) `hipMemsetAsync(ix_chunk)` (`:254`); (4) one persistent kernel `HlifCompressBatchKernel<CompressT,...>` with `grid = max_comp_ctas` (occupancy × CUs) and codec block size (`LZ4HlifKernels.hip:164-165` → `LZ4_COMP_THREADS_PER_CHUNK = warpsize`; `SnappyHlifKernels.hip:130-131` → `COMP_THREADS_PER_BLOCK = 2*warpsize`; `CascadedHlifKernels.hip` → `cascaded_compress_threadblock_size`). Inside (`hlif_shared.hiph:160-227`): block 0/thread 0 writes the CommonHeader; each CTA (or each `tiled_partition<warpsize>` when `chunks_per_block>1`) takes chunk `blockIdx.x*chunks_per_block+threadIdx.y`, compresses it into its private scratch slot `scratch_buffer + ix*max_comp_chunk_size` (`:181`), thread 0 reserves output space with a 64-bit `atomicAdd` on `comp_data_size` (`:197-203`) and stores the offset, the group copies scratch→final (`copyScratchBuffer`, `:127-158`: `char4` loads + 4 byte stores when scratch is 4-B aligned, else byte loop), propagates error status (`:216-220`), then grabs the next chunk via `atomicAdd(ix_chunk,1)` (`:222-225`) — dynamic work-stealing with `initial_chunks = gridDim.x*chunks_per_block`. Scratch = `max_comp_ctas * max_comp_chunk_size` (+ LZ4 hash tables, `LZ4Manager.hpp:147-151`), computed once in `finish_init` (`BatchManager.hpp:184-192`) from `hipOccupancyMaxActiveBlocksPerMultiprocessor × multiProcessorCount`.

**Decompression / format discovery**: `create_manager` (`arctoManagerFactory.cpp:65-148`) `hipMemcpyAsync`s the `CommonHeader` to host, **synchronises the stream**, switches on `format`, copies the codec's `FormatSpecHeader` (second sync), and constructs the matching manager (`LZ4Manager(uncomp_chunk_size, data_type…)`, `SnappyManager`, `GdeflateManager`, `BitcompManager` (if `ENABLE_BITCOMP`), `ANSManager`, `CascadedManager(options)`). `configure_decompression(buffer)` reads `decomp_data_size` and `num_chunks` with `hipMemcpyAsync` into pageable members (`ManagerBase.hpp:164-168`, `BatchManager.hpp:133-137` — the latter copies `sizeof(size_t)` = 8 bytes into the `uint32_t num_chunks` member, `arctoManager.hpp:118`; the extra 4 bytes land in struct tail padding, so benign today but UB). `decompress()` (`ManagerBase.hpp:230-251` → `BatchManager::do_decompress` `:103-122`) recomputes the table pointers from `num_chunks`, zeroes `ix_chunk`, and launches `HlifDecompressBatchKernel` (`hlif_shared.hiph:388-447`; LZ4 uses `chunks_per_block=2`, block `(warpsize,2)`, dynamic LDS `DECOMP_INPUT_BUFFER_SIZE*2`, `LZ4HlifKernels.hip:206-209`; Snappy `3*warpsize`; Cascaded `cascaded_decompress_threadblock_size`, all with the same work-stealing loop `:317-339`).

**Pinned-memory pool & status**: `PinnedPtrPool<T>` (`src/highlevel/PinnedPtrs.hpp`) pre-allocates 10 slots with one `hipHostMalloc` (`:61,84-97`), grows by 100 (`:62,162-173`), hands out RAII `PinnedPtrHandle`s returned to the free list on destruction (`:107-157,190-193`); `CompressionConfig`/`DecompressionConfig` each hold one (`CompressionConfigs.hpp:72-111`, `.cpp:54-58,112-118`), initialised to `arctoSuccess`; kernels write the pinned status *only on error* (`hlif_shared.hiph:216-220,328-332`) so the user can poll after a stream sync without a D2H copy. Each manager additionally pins `common_header_cpu` (`ManagerBase.hpp:116`) and a codec `format_spec` (`LZ4Manager.hpp:78`) and `hipMalloc`s a 4-byte `ix_chunk` (`BatchManager.hpp:93`).

**Stream/sync model**: all work goes on the `user_stream` captured at construction (`ManagerBase.hpp:85,105`); `compress/decompress` are async; `configure_compression` is host-only; `configure_decompression(buffer)` documents that it synchronises (`arctoManager.hpp:168`); `create_manager` synchronises twice; `get_compressed_output_size` is synchronous; scratch allocation is lazy on first `compress/decompress` and uses `hipMallocAsync` **only if `CUDART_VERSION >= 11020`** (`ManagerBase.hpp:190-194,211-215,238-243`) — `CUDART_VERSION` is undefined on HIP-clang, so **on AMD the manager always falls back to blocking `hipMalloc`/`hipFree` [verified]**; the `//: TODO check ROCm version` at `:239` acknowledges it.

### 2.7 Host staging (`arctoHostBatch`, `arctoHostBatchAdaptive`)

- `include/arcto/host_batch.h` + `src/lowlevel/HostBatch.cpp`: rationale at `host_batch.h:1-27` — scattered per-chunk `hipMemcpyAsync` from pageable vectors caps at ~6 GB/s; coalescing into one `hipHostMalloc`'d buffer and one `hipMemcpyAsync` reaches PCIe peak (~27 GB/s on RX 7900 XT, ~4.3×). Implementation: prefix-sum of chunk sizes (`HostBatch.cpp:34-38`), single `hipHostMalloc(hipHostMallocDefault)` (`:45`), `ChunkPtr/ChunkSize/Size/TotalSize` accessors (`:65-88`), `UploadAsync` = one H2D plus optional per-chunk device pointer fill-in (`:90-115`).
- `include/arcto/host_batch_adaptive.h` + `src/lowlevel/HostBatchAdaptive.cpp`: cost model (`host_batch_adaptive.h:51-71`): `t_total(W) = t_alloc(W) + ceil(input/W)·(t_h2h(W)+t_h2d(W)+t_kernel(W))`, each term ~linear in W, so `W_opt = max(W_kernel_sat, W_pcie_amort, W_launch_amort)` capped at the input size (`HostBatchAdaptive.cpp:128-154`). Priors: `R_alloc 0.22 GB/s`, `R_dram 11`, `R_pcie 25`, `R_kernel 30` (`:23-26`); floors `W_PCIE_AMORT 64 MiB`, `W_LAUNCH_AMORT 16 MiB`, `W_KERNEL_SAT_DEFAULT 64 MiB` (`:37-39`). **Per-arch tuned `W_kernel_sat = wave_slots × chunk_size_opt`** (`:43-75`): gfx906 15 MiB (960 slots×16 KB), gfx90a 52 MiB (3328×16 KB), gfx942 76 MiB (9728×8 KB), gfx1100 48 MiB (3072×16 KB), else 64 MiB. **Arch detection happens here and only here**: `pick_W_kernel_saturation()` → `hipGetDevice` + `hipGetDeviceProperties` + substring match on `props.gcnArchName` (`:63-73`); on the CUDA backend it returns the default because `cudaDeviceProp` has no `gcnArchName` (`:58-61`). Online refinement: EMA with α=1 on first sample then 0.2 (`:201-229`) — note the refined rates are **recorded but never fed back into `W_opt`** (the pinned buffer is never reallocated, `:143-152`; `adaptation_count` only gates α). Lifecycle: `Create → ChooseWindow (allocates once) → NextWindow/Upload/Record* loop → Destroy` (`host_batch_adaptive.h:24-49`).

## 3. AMD-relevant build/flag opportunities

Legend: **[V]** verified from code; **[T]** recommendation to test on hardware.

### 3.1 Make the HIP optimisation level explicit and add compile-time resource reports
- **[V]** Release relies on CMake's default `-O3 -DNDEBUG` for HIP; nothing in the project states it. Add `CMAKE_HIP_FLAGS_RELEASE` handling next to `CMakeLists.txt:152` and print it. Zero risk.
- **[T]** Add an opt-in `ARCTO_DEVICE_REPORTS` option that appends `-Rpass-analysis=kernel-resource-usage` (VGPR/SGPR/AGPR/LDS/occupancy/spill per kernel at compile time) and optionally `--save-temps` (emits `.s` ISA per offload arch) — `target_compile_options(arcto PRIVATE $<$<COMPILE_LANGUAGE:HIP>:…>)`. This is the cheapest way to validate every other item in this section without a profiler, and it would immediately show whether `HlifCompressBatchKernel`/`HlifDecompressBatchKernel` spill (they have no launch bounds, §3.6).

### 3.2 Per-arch flag sets
- **[V]** Today one flag set serves gfx90a/gfx942/gfx1100. CMake cannot vary flags per `--offload-arch`, but clang accepts them globally and ignores inapplicable ones, so per-arch tuning has to go through (a) separate build dirs per arch (already the natural mode given the wave-size macro, §3.3), or (b) code-level `#if defined(__gfx1100__)`/`__AMDGCN_WAVEFRONT_SIZE__`.
- **[T]** gfx1100 (RDNA3): `-mcumode` forces CU mode (a workgroup's waves share one CU's LDS/L0) instead of the default WGP mode; it sometimes helps LDS-heavy kernels (LZ4 decompress uses `DECOMP_INPUT_BUFFER_SIZE*2` dynamic LDS; Cascaded uses hipcub BlockScan/Reduce LDS) and sometimes hurts. Measure with the chunked benchmarks; apply only for gfx1100 builds.
- **[T]** `-mwavefrontsize64` on gfx1100: would let the wave64 code paths run on RDNA3 without `USE_WARPSIZE_32`, at the cost of RDNA3 executing wave64 over two passes; HIP's `warpSize` then reports 64 for that code object. Probably slower than native wave32; only worth a data point.

### 3.3 Fix the wave-size model so fat binaries work (design change, high value)
- **[V]** `USE_WARPSIZE_32`/`ENABLE_HIP_OPT_WARPSIZE64` are CMake-time globals (§1.6); a `gfx90a;gfx1100` fat binary cannot be correct for both targets, and nothing checks `hipDeviceProp_t::warpSize` against the compiled constant at runtime.
- **[T]** Device side: derive the lane count from the compiler's per-target macro (`__AMDGCN_WAVEFRONT_SIZE__`, or HIP's `warpSize` constant) inside `arcto_device_types.h`, `amd_optimizations.h`, `LZ4Kernels.hiph:87-103`, `snappy/config.h:45-53` instead of the CMake macro. Host side (launch dims like `LZ4_COMP_THREADS_PER_CHUNK`, `COMP_THREADS_PER_BLOCK`, occupancy queries) would need `hipDeviceProp_t::warpSize` at runtime or templated host dispatch. Interim, low-effort guard: at manager/batch entry, assert once that `props.warpSize == arcto::warpsize` and return `arctoErrorNotSupported` otherwise; add a configure-time `message(WARNING)` if `CMAKE_HIP_ARCHITECTURES` mixes gfx9 and gfx10+/gfx11 targets.

### 3.4 Flags that are *not* worth adding (checked)
- **[V]** `-munsafe-fp-atomics`: there are **no floating-point atomics** in ARCTO sources (the only atomics are `atomicAdd` on `unsigned long long`/`uint32_t` in `hlif_shared.hiph:200,223,335`; the vendored zfp uses integer `atomicAdd`/`atomicXor` on its bit-stream words, `third_party/zfp/src/hip/variable.h:107,150`, `writer.h:20`). The flag is a no-op here.
- **[V]/[T]** `-ffast-math` (or `-Ofast`): ARCTO's own codecs are integer-only; the vendored zfp HIP encoder uses `frexp/ldexp`, float×power-of-two scaling and float→int conversion (`third_party/zfp/src/hip/encode.h:42-102`, `decode.h:20-27`). `-ffast-math` implies `-ffinite-math-only`/`-fno-signed-zeros`/`-freciprocal-math`, which can change NaN/Inf/−0 handling and therefore the bit-stream — `tests/test_zfp_bitcompat.cpp` would catch it, but there is no upside for the integer codecs. Recommendation: **do not** add globally; if ever, apply per-target and never to `zfp`. (HIP already defaults to `-ffp-contract=fast-honor-pragmas`; zfp's float path has no add-multiply pairs to contract.)
- **[V]** `-fgpu-rdc`: not used; all kernels are fully instantiated in their own TU (templates in `.hiph` headers), so whole-TU device compilation is already the best case for inlining. Only needed if device functions were ever split across TUs. Keep off.
- **[T]** LTO (`-flto` host, `-foffload-lto` device): little expected gain for device code for the same reason; host-side LTO could shave a bit off the many small host wrappers. Low priority.

### 3.5 hipcc vs clang driver differences to be aware of
- **[V]** CMake's HIP language drives `clang++` directly (no `hipcc` anywhere in the tree). hipcc historically appends `-mllvm -amdgpu-early-inline-all=true -mllvm -amdgpu-function-calls=false` (force full inlining of device functions); the CMake/clang path does **not** unless you add them. **[T]** Try `$<$<COMPILE_LANGUAGE:HIP>:-mllvm;-amdgpu-early-inline-all=true;-mllvm;-amdgpu-function-calls=false>` on `arcto` and compare both perf and compile time; the HLIF wrappers (`compress_chunk`/`decompress_chunk` called through template objects) and the Snappy decoder state machine are the likely beneficiaries if clang decided not to inline something. Check with `-Rpass-analysis` whether any real (non-inlined) calls exist first.
- **[V]** `__launch_bounds__` second argument means waves-per-EU on HIP (see §2.1). Any value copied from CUDA-style "min blocks per SM" reasoning should be recomputed (`MIN_WARPS_PER_EU = MIN_BLOCKS × THREADS_PER_BLOCK / warpsize / 4 SIMDs` roughly) or expressed directly with `__attribute__((amdgpu_waves_per_eu(min,max)))` / `amdgpu_flat_work_group_size(min,max)` which are unambiguous.

### 3.6 Launch bounds / occupancy attributes (shared kernels)
- **[V]** `HlifCompressBatchKernel`/`HlifDecompressBatchKernel` (`hlif_shared.hiph:232-273,391-447`) carry **no** `__launch_bounds__`. On AMD the default `amdgpu_flat_work_group_size` is 1..1024, which forces the compiler to budget registers for a 1024-thread workgroup (≈128 VGPRs/wave on CDNA) even though the real blocks are 64/128/192 threads. **[T]** Add a `template<int MaxThreads>` (or make `chunks_per_block×threads` a template parameter) and `__launch_bounds__(MaxThreads)`; or add `__attribute__((amdgpu_flat_work_group_size(MaxThreads,MaxThreads)))` on AMD. Low risk, potentially fewer spills for the Snappy/LZ4 wrappers. The low-level Snappy kernels already do this (`SnappyBatchKernels.hip:65,84,145`); the vendored zfp uses `__launch_bounds__(256,1)` (`third_party/zfp/src/hip/encode3.h:47`).
- **[V]** `amd_optimizations.h` bounds are applied only to Cascaded primitives; `AMD_LAUNCH_BOUNDS_HIGH_OCC` is unused. Re-express them as `amdgpu_waves_per_eu` with per-arch reasoning (CDNA3: 512 VGPRs/SIMD, 8 waves max per SIMD in wave64… vs RDNA3 wave32 with 1536 VGPRs/SIMD); **[T]** measure with `-Rpass-analysis`.

### 3.7 Build-hygiene items with AMD impact
- **[V]** `-g -ggdb` for HIP debug (`CMakeLists.txt:160`) compiles *device* code with debug info; combined with no `-O`, Debug-build kernels are much slower and can spill — fine for debugging but don't benchmark Debug (the comment about `-G` shows the authors hit this on CUDA).
- **[V]** No warnings reach HIP TUs (`:196`). **[T]** Add `-Wall -Wextra -Wno-unused-parameter` for `COMPILE_LANGUAGE:HIP` under `DEVEL` — clang will flag things like the unknown `likely_uniform` attribute and unused `volatile` the day they are instantiated.
- **[V]** `hip::hipcub` found but not linked (`CMakeLists.txt:122`, `src/CMakeLists.txt`): link `PRIVATE hip::hipcub` (or `roc::rocprim`) to make the include path explicit and to pick up its interface defines; today it works by accident of `/opt/rocm/include`.

## 4. Shared-infra optimisation opportunities

Each: where / what / mechanism / impact / risk / effort / how to measure. Impact levels are expectations, not measurements (**[T]** unless stated).

### 4.1 HLIF pipeline (`src/arcto_common_deps/hlif_shared.hiph`, `src/highlevel/*`)

1. **Output copy is byte-granular** — `copyScratchBuffer` (`hlif_shared.hiph:127-158`) loads `char4` but writes four **byte stores** per thread (`:144-147`), or a pure byte loop when scratch is not 4-B aligned. On GCN/CDNA/RDNA each byte store is a separate `buffer/global_store_byte`; the final destination `comp_buffer + comp_chunk_offset` is arbitrarily aligned because offsets come from `atomicAdd` of raw sizes (`:200-202`). *Mechanism:* reserve `roundUpTo(comp_chunk_size, 16)` in the atomic (keeps every chunk 16-B aligned; readers use the per-chunk offset table so the format remains decodable by unmodified readers; `comp_data_size` then includes padding), then copy with `uint4`/`dwordx4` loads+stores and a byte tail. *Impact:* medium for fast codecs (LZ4/Snappy compress are close to memory-bound on the copy for incompressible data: the compressed bytes are written twice). *Risk:* low-medium (output size grows by ≤15 B/chunk; `get_compressed_output_size` still correct; any consumer that assumed gap-less packing would see gaps). *Effort:* small. *Measure:* `benchmark_lz4_chunked` on `synth_random_1mb.bin` style inputs (ratio≈1) before/after; rocprof `FETCH_SIZE/WRITE_SIZE`.
2. **Three extra stream ops per call** — `hipMemcpyAsync(format header)`, `hipMemsetAsync(comp_data_size)`, `hipMemsetAsync(ix_chunk)` before the compress kernel (`ManagerBase.hpp:222-224`, `BatchManager.hpp:254`) and one memset before decompress (`BatchManager.hpp:114`). On ROCm each is a separate blit kernel/copy packet (~5–20 µs each). *Mechanism:* a 1-block init kernel that writes the CommonHeader (already done by block 0 in the main kernel), the format header (pass it by value as a kernel arg — it is tiny) and zeroes both counters; or keep `ix_chunk` and `comp_data_size` in one 16-B device struct zeroed by a single memset. *Impact:* visible only for small buffers (<~8 MB) or many calls. *Risk:* low. *Effort:* small. *Measure:* rocprof/`rocprofv3` kernel timeline, or wall-clock of 1000 `compress()` calls of 1 MB.
3. **Per-chunk global atomics for work stealing** — two global atomics + two `cg_group.sync()` per chunk (`:197-225`, `:334-338`). With 64 KB chunks this is negligible; with 4–8 KB chunks (the gfx942 sweet spot per `HostBatchAdaptive.cpp:47`) the atomic on a single address becomes a serialisation point across up to ~300 CUs × occupancy CTAs. *Mechanism:* grab chunks in batches (atomicAdd by `k`, process `k` consecutive chunks), or static striding when `num_chunks ≤ initial_chunks × small factor`. *Impact:* low–medium on MI300X with small chunks. *Risk:* low. *Effort:* small. *Measure:* chunk-size sweep (`-p 4096 … 65536`) on gfx942 HLIF path.
4. **Persistent-grid sizing uses `hipGetDeviceProperties` per manager** (§2.3) and `hipOccupancyMaxActiveBlocksPerMultiprocessor`; both cheap enough per manager but `hipGetDeviceProperties` on ROCm is a heavyweight call. *Mechanism:* a process-wide cached `DeviceInfo` in `HipUtils` (CU count, warpSize, gcnArchName, maxSharedMemoryPerBlock, L2 size). *Impact:* only for code that creates managers per call (the benchmark's per-iteration `create_manager`-style patterns). *Risk:* none. *Effort:* small.
5. **Lazy scratch allocation is synchronous on AMD** (`ManagerBase.hpp:211-215,238-243`, `CUDART_VERSION` guard). *Mechanism:* `#if defined(CUDART_VERSION) ? CUDART_VERSION>=11020 : HIP_VERSION>=50300000` → `hipMallocAsync/hipFreeAsync` (stream-ordered allocator, ROCm ≥ 5.3). *Impact:* removes a device-wide sync on first use and on `set_scratch_buffer`; matters in pipelines that create managers on the fly. *Risk:* low (fallback retained). *Effort:* trivial.
6. **Pinned allocations per manager** — each manager does ≥3 `hipHostMalloc` (common header, format spec, status pool) + `hipMalloc(ix_chunk)`. `benchmark_template_chunked.cuh:451-456` documents a measured "~13-iteration side effect" of `hipHostMalloc` on subsequent kernels on gfx1100. *Mechanism:* one pinned arena per manager (or per process) carved for header+format+status pool; `ix_chunk` could live in the pinned arena too (device atomics on fine-grained host memory are slow — keep it device-side) or share the `hipMalloc` with the scratch buffer. *Impact:* construction cost + the gfx1100 anomaly. *Risk:* low. *Effort:* small–medium.
7. **`configure_decompression(buffer)` copies into pageable members** (`ManagerBase.hpp:164-168`, `BatchManager.hpp:133-137`): D2H into pageable memory makes the "async" copy effectively synchronous and the `uint32_t` target is 4 B too small. *Mechanism:* copy the whole `CommonHeader` into the already-pinned `common_header_cpu` with one `hipMemcpyAsync` + event, then read the fields. *Impact:* latency + correctness hygiene. *Risk:* none. *Effort:* trivial.
8. **Device writes to pinned status on error only** — good; keep. But `kernel_output_status` is written without a fence; visibility is guaranteed at stream sync only. Document.

### 4.2 `HipUtils`
- Add the cached `DeviceInfo` (above) and a `warpSize` consistency check (§3.3).
- `device_pointer()` is called 6–7× per low-level batch call (`LZ4Batch.cpp:107-117`). On ROCm `hipPointerGetAttributes` costs a few µs each → ~20–50 µs per API call of pure host overhead, comparable to a kernel launch. *Mechanism:* make the attribute check debug-only, or check once per distinct pointer via a tiny LRU, or accept the pointer as-is (the CUDA backend path already special-cases versions). *Impact:* small-buffer/high-call-rate workloads. *Risk:* loses an early error for host pointers (the kernel would fault instead). *Effort:* trivial. *Measure:* host-side timer around `arctoBatchedLZ4CompressAsync` with an empty stream.

### 4.3 `TempSpaceBroker`
- Sub-buffer alignment is `alignof(T)` (≤ 8 B) (`TempSpaceBroker.h:78-88`). Device-friendly alignment is ≥ 16 B for `dwordx4` loads and ideally 128/256 B (cache-line / `hipMalloc` granularity) for per-CTA regions such as LZ4 hash tables. *Mechanism:* `max(alignof(T), 256)` (or a constructor parameter); callers already over-provision temp space via the codec's `GetTempSize`, so check those formulas add the slack (they are computed host-side with the same broker logic in `LZ4CompressionKernels.hip`). *Impact:* small but free; it also future-proofs vectorised loads. *Risk:* temp-size estimates must include the extra padding (otherwise `reserve` throws). *Effort:* small.

### 4.4 Host staging
- **[V]** `arctoHostBatchAdaptive` computes rates online but never re-derives `W_opt` from them (§2.7). Either wire `R_*` into a second-window re-choice (with the documented "never realloc" caveat → choose `W_opt` after a first probe window of `W_launch_amort` size), or document the model as priors-only. *Impact:* correctness of the claim in `host_batch_adaptive.h:66-71`. *Effort:* small.
- **[T]** `hipHostMalloc(hipHostMallocDefault)` everywhere (`HostBatch.cpp:45`, `HostBatchAdaptive.cpp:149`). For pure H2D staging on ROCm, `hipHostMallocNumaUser`/`hipHostMallocWriteCombined`-style flags or `hipExtHostAlloc` with coarse-grained memory can raise H2D throughput and avoid the fine-grained coherence cost; the benchmark's documented gfx1100 anomaly after `hipHostMalloc` is also worth re-testing with non-coherent flags. Use the `-P`/`-A` benchmark modes with `-R` for A/B.
- **[T]** Double-buffer the adaptive window (two pinned windows, memcpy of window N+1 overlapping H2D/kernel of window N) — the cost model at `host_batch_adaptive.h:51` is explicitly "single-buffered, no overlap"; overlap would hide `t_h2h` almost entirely. *Effort:* medium (API gains a second buffer / event handshake).
- **[V]** Arch detection uses substring match on `gcnArchName` (`HostBatchAdaptive.cpp:68-72`) — note `gcnArchName` includes feature suffixes (`gfx90a:sramecc+:xnack-`), so substring is the right choice; gfx940/941 and gfx950 fall to the default — add them when measured.

### 4.5 Benchmark harness (measurement fidelity, AMD-specific)
- Per-iteration `hipMalloc`/`hipFree` of temp, output and **one `hipMalloc` per chunk** (`benchmark_template_chunked.cuh:695-698,776-778`) sit outside the timed region but inflate wall-time and fragment the device heap; for 1600 chunks that is 3200 allocator calls per iteration. Replace with one allocation sliced by prefix sum (the `BatchData` class already does this for inputs). Not a perf result change, but makes `-i 100` sweeps practical.
- `hipEventCreate` default flags are fine; consider `hipEventCreateWithFlags(hipEventDefault)` unchanged; nothing to do.
- The decompress output verification copies chunk-by-chunk D2H (`:757-774`) only on the last iteration — fine.

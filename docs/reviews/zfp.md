### 1.3 Decompress call chain, per mode
`arctoZFPDecompress` (`ZFPBatch.cpp:413-556`):
1. `parse_header` (`:337-361`) on host (serial stream; no HIP exec).
2. Trailer sniff: last 20 bytes, magic `0x50465A41` at tail+16 (`:441-463`).

4. Payload bitstream on `h_input + header_bytes` (`:489-490`); header re-parsed a second time to copy params (`:504-511`); index reconstructed pointing **into h_input** (`:513-534`); `zfp_stream_set_execution(hip)` (`:538`) → one `device_init()`.
5. `zfp_decompress` (`zfp.c:1407-1527`): `require_index` for non-fixed-rate (`:1470`); reads the 8-B index header **on the host** (`:1494-1496`, dereferences `index->data`), advances `index->data` by 8 B but leaves `size` unchanged (`:1499-1505`); → `zfp_internal_hip_decompress` (`hip/interface.cpp:134-238`):

   - `setup_device_stream_decompress` (`hip/device.h:161-171`): **hipMalloc + sync H2D of `stream_capacity` (= payload bytes)**.
   - variable-rate: index type must be offset/hybrid (`:184-189`); `setup_device_index_decompress` (`hip/device.h:185-195`): hipMalloc + sync H2D of `index->size` bytes starting at the advanced pointer (reads 8 B past the index — upstream bug, harmless in ARCTO since the trailer follows).

### 1.4 ARCTO's in-band index format (variable-rate only)
`[canonical header][payload (word-aligned)][zfp offset index: u32 type, u32 granularity, u64 start-offset × chunks][20-B trailer: u8 type, 3×0, u32 granularity, u64 index_bytes, u32 magic 'AZFP']` (`ZFPBatch.cpp:108-119, 293-320`). With granularity 1 the index costs **8 B per 64 values = 1 bit/value** (§5 D3). Canonical serial decoders ignore the trailer (they stop at the payload); GPU decode of canonical variable-rate streams without it falls back to CPU serial.

### 1.5 HIP backend structure
- Generated from `src/cuda` by `hipify-perl` + sed (`hip/Makefile:1-39`). Normalized diff cuda→hip shows only: added `#include "hip/hip_runtime.h"`, `cuda_block_size` names kept, `CUDART_VERSION` guards left as-is (undefined → 0 → full `#pragma unroll`, equivalent), `hipHostMalloc/hipHostFree`, `hipError_t`, `hipDeviceProp_t`, include order in `shared.h`. **Functionally identical to the CUDA backend, including `variable.h` (in-place compaction) and `writer.h`.**
- One kernel per dimensionality for encode and decode, templated on Scalar ∈ {int, long long, float, double}: `encode{1,2,3}_kernel`, `decode{1,2,3}_kernel`. Mapping: **one thread = one zfp block** (4 / 16 / 64 values), `block_idx = global thread id` (`encode3.h:61-64`), 128-thread 1-D workgroups (= 2 wave64 on CDNA, 4 wave32 on RDNA3), grid from `calculate_grid_size` (`shared.h:77-102`; 1-D unless > `maxGridSize.x`). Decode additionally has a `granularity` loop (g blocks per thread, `decode3.h:68-69, 84-105`).
- Per-thread pipeline (encode): gather 64 scalars (`encode3.h:11-17`), `max_exponent` (`encode.h:74-84`), `fwd_cast` to `Int iblock[64]` (`:106-118`), `fwd_xform` lifting (`:174-192`), `fwd_order`+`int2uint` into `UInt ublock[64]` using `perm_3` (`:220-233`; `constants.h:47-131`), then `encode_ints` / `encode_ints_prec` (`:235-302`): per bit plane, build the 64-bit plane with 64 shift/and/or ops (`:251-252`), write the first n bits (`:256`), then the **bit-by-bit unary group-test loops** (`:258-260`), `flush` (`:264`). Identical grammar to the CPU `encode_few_ints` (`template/encode.c:91-132`) — there is no faster upstream variant to port.
- Bitstream writer `BlockWriter` (`hip/writer.h`): 64-bit `Word` buffer, `write_word` = `atomicAdd(ptr++, w)` on `unsigned long long` (`:19-20`) because adjacent blocks can share a word when `maxbits % 64 != 0`; relies on the prior `hipMemset` zero-fill. Block b writes at bit `b×maxbits` (`encode3.h:86`).
- Reader `BlockReader` (`hip/reader.h`): plain 8-B loads (`:20`), `rseek` at `b×maxbits` (fixed-rate, `decode3.h:77-78`) or at `block_offset(d_index, …)` (`decode.h:407-435`; offset index = direct load; hybrid path is warp-32 shared-memory code, see §3).
- Variable-rate: encode kernels write each block into a fixed `maxbits`-bit slot and record its length in a `ushort` index (`encode3.h:101-102`); `compact_stream` (`variable.h`) scans lengths to offsets (hipcub) and compacts in place with a cooperative kernel (LDS staging + funnel shifts + LDS atomics + coalesced stores; `atomicXor` only on subchunk boundary words, `:145-152`).

## 3. NVIDIA-isms and AMD pitfalls (concrete)

1. **Mechanical hipify leftovers**: `CUDART_VERSION` guards (`encode.h:111,226,246,280`; `decode.h:36,163,191,225`) — undefined under hipcc → branch to plain `#pragma unroll` (full unroll) — benign; `cuda_block_size` identifiers (`encode{1,2,3}.h`, `decode{1,2,3}.h`).
2. **Warp-32 hard-coding in the hybrid-index path** (`decode.h:415-432`): `(chunk_idx - thread_idx) / 32`, `warp_idx * 9` (1 u64 + 32 u16 = 72 B), `__shared__ uint64 offset[32]`, prefix sum assumes 32 threads, `__syncthreads()` inside a device function under divergent control flow; but the kernels launch **128** threads (`decode3.h:131`, comment at `:130` still says "fixed to 32") → `offset[thread_idx]` with `thread_idx` up to 127 is an out-of-bounds LDS access — broken upstream on any GPU, doubly so with wave64. ARCTO only ever sets `zfp_index_offset` (`ZFPBatch.cpp:280`) and the trailer type byte is read back (`:523-525`) — a malicious/foreign trailer with type=3 would reach this path; consider rejecting hybrid in the wrapper.
3. **`__launch_bounds__(256, 1)` semantics** (`encode3.h:47`, `decode3.h:41`): in HIP-Clang the second argument is "min waves per EU" (`amdgpu_waves_per_eu`), not CUDA's min-blocks-per-SM; with value 1 the compiler is free to use the whole VGPR budget (up to 256 arch VGPRs + AGPRs on gfx90a/gfx942) → likely 1–2 waves/SIMD; and the kernel is launched with 128 threads anyway. (Verify on hardware: resource usage report.)
4. **SM-centric constants**: 48 KB LDS cap (`variable.h:329`) — AMD allows 64 KB per workgroup (CDNA2/3, RDNA3), so the tile tiers are conservative; `threads_per_sm = 1024` for chunk sizing (`device.h:200`) — CDNA CUs hold 2048 threads; both only affect chunking/LDS tiers, not correctness.
5. **64-bit `atomicAdd` per emitted word** (`writer.h:20`): on AMD global atomics are executed in L2 (TCC) and bypass L1; fine on coarse-grained `hipMalloc` memory (ARCTO's case), but would be slow/unsupported on fine-grained or host-pinned memory — never point `stream->begin` at pinned host memory expecting zero-copy. Atomics are only *needed* on the first/last word of a slot, and never when `maxbits % 64 == 0` (integer fixed rate).
6. **Thread-per-block mapping on wave64**: the data-dependent unary loops (`encode.h:258-260`, `decode.h:186-188`) diverge per block; a wave64 runs each loop until the slowest of 64 blocks finishes (vs 32 on NVIDIA) → longer tails; and small fields under-fill the GPU (a 64³ cube = 4096 blocks = 64 wave64 for a 440-SIMD MI250X GCD; the 1-MB `tests/data/*` cubes are exactly that size).
7. **Strided scalar gathers/scatters** (`encode3.h:11-17`, `decode3.h:9-17`): each VMEM instruction touches 64 lanes × 4 B at 16-B stride; AMD TCP L1 is small (16 KB gfx90a, 32 KB gfx942) and write-through, so the decoder's 64 partial-line stores per thread rely on L2 write-combining; the row (4 consecutive scalars) is a natural `dwordx4`.
8. **Cooperative groups** (`variable.h:14,193,248`; `hipLaunchCooperativeKernel :307`): supported on ROCm for CDNA2/3 and RDNA3 but `grid.sync()` is a software global barrier (atomics + fences) — slower than NVIDIA's; all WGs must be co-resident (occupancy query `:289-294`).
9. **`malloc_async`/`free_async` are plain `hipMalloc`/`hipFree`** (`share/device.h:95-105`) whereas the CUDA backend uses `cudaMallocAsync/cudaFreeAsync` on CUDA ≥ 11.2 (`:43-60`); on ROCm `hipFree` implies a device-wide synchronization.
10. **`is_gpu_ptr` excludes managed memory** (`share/device.h:83-87` only `hipMemoryTypeDevice`; CUDA also accepts `cudaMemoryTypeManaged`, `:30-32`) → `hipMallocManaged` fields/streams are silently staged through extra copies.
11. **64-bit integer division/modulo by runtime values** (`encode3.h:78-80`, `decode3.h:90-92`, 2-D variants): no hardware integer divide on AMD; 64-bit is a long software sequence (hundreds of VALU ops for 3 div + 3 mod) per block.
12. **NULL-stream everything**: kernels (`encode3.h:142`, `decode3.h:156`), memsets, memcpys; no way to overlap with the application's streams; `hipFree` syncs.
13. **Static `__shared__` inside an inlined device function** (`decode.h:423`) costs 256 B LDS per workgroup for every decode launch even when unused — negligible, but it is there.

## 4. Gap analysis: HIP vs CUDA backend inside the submodule

- **Features: no lag.** `hip/variable.h` = `cuda/variable.cuh` (compaction, `copy_length_kernel`, cooperative `compact_stream_kernel`, `align_stream_kernel`), `hip/writer.h` = `cuda/writer.cuh`, encode/decode 1–3-D for int32/int64/float/double, offset + hybrid index decode. Both lack 4-D (`zfp.c:1351/1355`), reversible (`interface.cpp:57-62`), and non-contiguous host fields (`device.h:229,253`). **ARCTO's `ZFPBatch.cpp` re-implements none of this**; it only (a) separates header/payload buffers to work around the kernel writing from word 0, and (b) serializes the canonical offset index in-band with a trailer.
- **Performance-technique gaps (HIP-specific)**: (1) no async allocation (`hipMallocAsync`), (2) managed-memory detection, (3) otherwise identical — meaning every NVIDIA-shaped decision (thread-per-block, 128-thread WGs, 48 KB LDS, warp-32 hybrid path, atomics per word) is inherited verbatim. The `SHFL_XOR` macro differs (`share/device.h:16` vs `:71`) but is unused in both backends.

## 5. Optimization opportunities

Legend — Effort S/M/L; "Bitstream": must be preserved (all items below are designed to be bit-identical; T1 is the gate). Expected impact is an estimate (no hardware).

### 5.0 Prerequisite: T1 — byte-exact regression gate (S)
Current tests are tolerance-based (`tests/test_zfp_bitcompat.cpp:9-12, 143-146, 196-199`; `tests/test_zfp_canonical.cpp:143-150`) on a 64×64×32 float field. Add a test that compares the **payload region** `[header_bytes, header_bytes+payload_bytes)` produced by the HIP path against `zfp_exec_serial` byte-for-byte (fixed-rate K ∈ {8, 12.5, 16, 24} incl. a non-integer rate to exercise word sharing; fixed-precision; fixed-accuracy; float/double/int32/int64; shapes with `nx%4≠0`, 1-D/2-D; all-zero blocks). Every kernel change below should be gated by it. Measure: `ctest`.

### 5.1 COMPRESSION (kernel side, inside the fork)
| ID | Title / where | What | Mechanism on CDNA2/CDNA3/RDNA3 | Impact | Risk | Effort | Measure |
|---|---|---|---|---|---|---|---|
| C1 | Vectorized row gather — `gather3/gather2` (`encode3.h:11-17`, `encode2.h:11-16`) | When `sx==1` and row start is 16-B aligned, load each x-row as one `float4`/`double2`(x2) instead of 4 scalars; scalar fallback otherwise (partial blocks stay scalar) | Lanes hold consecutive x-blocks → each row-load instruction covers a contiguous 1 KB per wave64 (fully coalesced `global_load_dwordx4`), 4× fewer VMEM instructions (float), lower TA/TD pressure; helps MI300X most (VMEM issue bound) | Medium on encode (input read is the largest memory stream at K≤16) | Alignment: requires `sy,sz` multiples of 4 elements for float (nx%4==0, contiguous); else per-row fallback (AMD supports unaligned `dwordx4` but slower across lines — verify) | S | `benchmark_zfp_single -3 512,512,512 -m fixed_rate -r 16`; rocprof `SQ_INSTS_VMEM_RD`, `FETCH_SIZE` |
| C2 | Atomic only on slot-edge words — `BlockWriter::write_word` (`writer.h:19-20`) | Track word index within the block; use plain store for interior words, `atomicAdd` only for the first/last word of the slot; when `maxbits%64==0` no atomics at all | Removes L2 RMW atomics for ≥87 % of words (K=16: 14 of 16); same trick upstream uses in `store_subchunk` (`variable.h:145-152`) | Low–medium alone; enabler for C3/C9 | Pre-zeroing must remain (padding beyond `bits` is supplied by memset) | S | rocprof `TCC_ATOMIC`/`TCC_EA_ATOMIC`, encode time |
| C3 | Word-aligned *slots* for variable-rate + drop memset — `interface.cpp:86` (slot stride), `encode3.h:86,133-134`, `variable.h:228` | Decouple the encoder bit budget (`maxbits`, canonical) from the uncompacted slot stride: stride = `round_up(maxbits,64)`. Then no two blocks share a word → all plain stores (no atomics) and the **memset can be dropped**: compaction reads exactly `length` bits per block and masks the tail (`variable.h:64-71, 103-104`), so slot garbage is never observed | Fixed-accuracy float 3-D slot is 2120 b → memset ≈ 1.03× input size + a 1.06× input device allocation per call; removing memset saves a full HBM write pass; no atomics | Medium (var-rate) | Slots are scratch, never serialized → bitstream untouched; must keep `with_maxbits<>()` budget logic identical; fixed-rate keeps exact `maxbits` stride (it *is* the output layout) and either memset or explicit in-kernel zero padding of the slot (serial writes `stream_pad`; GPU currently relies on memset — the padding bytes must be zero) | S–M | T1; encode time; `hipMemset` disappears in rocprof trace |
| C4 | SWAR bit-plane transpose — `encode_ints/_prec` step 1 (`encode.h:251-252, 285-286`) and decoder deposit (`decode.h:196-197, 230-231`) | Build all planes once with a recursive 64×32 (float) / 64×64 (double) bit-matrix transpose on `uint64` words (Hacker's Delight §7-3 style), then read `planes[k]`; decoder: store `planes[k]=x`, inverse-transpose once at the end | ~8 K VALU ops/block for extraction today (64×4 ops×32 planes) → ~0.5–1 K; pure data movement, no FP | Medium–high (encode+decode are ALU/latency bound, not bandwidth bound, with thread-per-block) | Register pressure (planes[32] u64 = 64 VGPRs; `ublock` dies after transpose → roughly neutral); bit-exact | M | rocprof `SQ_INSTS_VALU`; T1 |
| C5 | Remove 64-bit div/mod — `encode3.h:77-80`, `encode2.h:67-69` (and decoders `decode3.h:89-92`, `decode2.h:82-84`) | Use 32-bit math when `blocks < 2^32` (always, in practice), or map a 3-D grid (blockIdx.y/z ↔ by/bz) so x/y/z need no division, or pass precomputed reciprocals | 3 div + 3 mod in 64-bit ≈ 500–1000 VALU ops/block on AMD (software division) | Low–medium (5–10 % of per-block ALU) | none; bit-exact | S | `SQ_INSTS_VALU`, time |
| C6 | Occupancy / launch-bounds / flags — `encode3.h:47,121`, `decode3.h:41,131`; zfp HIP flags | Report resource usage (`-Rpass-analysis=kernel-resource-usage` or `--save-temps` → `.vgpr_count/.agpr_count/.private_segment_fixed_size`) per arch; sweep `__launch_bounds__(128, W)` W∈{2,3,4} and WG size {64,128,256}; keep `-O3`; **never** enable `-ffast-math`/DAZ (would change `exponent()` on subnormals, `encode.h:55-72`); HIP's default `-ffp-contract=fast` is harmless (no a·b+c in `fwd_cast`/`inv_cast`, `encode.h:117`, `decode.h:42`) | With waves_per_eu(1) the compiler may allocate ~200–256 VGPRs → 1–2 waves/SIMD on CDNA; doubles likely spill to AGPR/scratch; RDNA3 (1536 VGPRs/SIMD wave32) less affected | Unknown until measured; potentially medium | spills if over-constrained | S | resource report; rocprof `MeanOccupancyPerCU`, scratch traffic; time |
| C7 | (L) Wave-cooperative 3-D block encode — new kernel beside `encode3_kernel` | 16 lanes per block (one x-row of 4 values per lane, loaded as `dwordx4`) → 4 blocks per wave64 (2 per wave32); lifting along y/z via DPP/`__shfl_xor` within the 16-lane group; per-plane bits via `__ballot` (wave64 ballot returns the 64-bit plane directly — a natural AMD fit); serial group-test coder on one lane per block unless combined with C8 | Eliminates the 192-VGPR-per-thread footprint (occupancy ↑), perfectly coalesced gathers, 16–64× more waves for small fields (64³ cube: 4096 waves instead of 64) | High for small/medium fields; uncertain for large ones unless C8 lands (otherwise 4/64 lanes busy during coding) | Large; coefficient permutation must be applied before ballot (lane shuffle); correctness subtle | L | prototype only after C1–C6/C8; T1 |
| C8 | ctz-based run-length coder (bit-exact) — `encode_ints` steps 2–3 (`encode.h:256-260`), `encode_ints_prec` (`:288-291`) | The remainder of a plane after the first n bits is: while x≠0 → emit `1`, then `t=ctz(x)` zeros and a `1` (unless n reaches BlockSize−1 where the loop bound truncates), advance n by t+1; when x==0 and n<BlockSize → emit `0`. Emit with `write_bits` in O(popcount) steps, clamping to the fixed-rate `bits` budget (truncation of the same bit string) | Replaces up to 64 divergent `write_bit` iterations per plane (each with a compare/branch and buffer update) with ≤popcount iterations; on wave64 the loop runs to the slowest lane, so AMD gains more | Potentially the largest kernel-side win (the coder dominates) | Subtle corners (`n < BlockSize-1`, budget exhaustion mid-run); needs an exhaustive unit test vs the serial coder over random planes + T1 | M | T1 + exhaustive plane test; time |
| C9 | LDS-staged coalesced output (fixed-rate) — new path in `encode3_kernel`/`BlockWriter` | A wave's 64 blocks occupy a contiguous `64×maxbits`-bit span (block b at b×maxbits): write each block's words to LDS (per-block stride padded to `W+1` words to avoid 64-way bank conflicts when W is a multiple of 16), zero-fill the slot in LDS, then store the span with coalesced `dwordx4` plain stores → no atomics, no memset | Today each word-write instruction touches 64 distinct lines for 512 B useful (12.5 % line use, relies on L2 merging) | Medium on encode | LDS budget: K=16 → 8 KB/wave (caps at ~8 waves/CU), K=32 → 16 KB/wave; only for integer rates / aligned slots | M | `TCC_REQ`, `WRITE_SIZE`, time |

### 5.4 Suggested order
1. T1 (gate), H1, D4, H2(a), H4 — small, host-side, no bitstream risk, big wins for small/medium fields.
2. C1/D1, C5, C3, C2, C6/D5 — small kernel changes, measurable with rocprof.
3. C4, C8, D2, C9, D3, H2(b)/H3/H7 — medium; C8 likely the largest kernel-side win.
4. C7 — only with data from the above.

### 5.5 Measurement recipe
- Build with `-DBUILD_BENCHMARKS=ON -DBUILD_TESTS=ON`; optionally `-DZFP_WITH_HIP_PROFILE=ON` on the zfp target (`hip/shared.h:4-5`, `encode3.h:136-157`, `decode3.h:150-174`) to print **kernel-only** GB/s via hipEvents — this separates kernel time from the host overheads of §1.6.
- `benchmark_zfp_single -f cube.bin -3 NX,NY,NZ -m {fixed_rate|fixed_precision|fixed_accuracy} -r P -i 10 -w 2 [-c] [-D]` (`benchmark_zfp_single.cu:76-94`); it times wall-clock around `arctoZFPCompress/Decompress` (`:310-320`) so it captures all host-side costs; fidelity columns (max_abs, RMSE, PSNR, max_rel, `:152-191`). The shipped `tests/data/*` are 64³ (1 MB): generate ≥256³–512³ synthetic cubes for kernel-throughput work, and keep 64³ to quantify fixed overheads.
- rocprof/omnitrace: API trace (hipMalloc/hipFree/hipMemcpy/hipMemset counts and durations), counters `SQ_INSTS_VALU`, `SQ_INSTS_VMEM_RD/WR`, `FETCH_SIZE`, `WRITE_SIZE`, `TCC_REQ`, `TCC_HIT`, `TCC_EA_ATOMIC`, `MeanOccupancyPerCU`; compile with `-Rpass-analysis=kernel-resource-usage` for VGPR/AGPR/LDS/scratch per kernel per arch.
- Correctness: `ctest` (`test_zfp_canonical`, `test_zfp_bitcompat`) + T1.

## 6. Open questions to verify on hardware
1. Actual VGPR/AGPR/scratch and occupancy of `encode3_kernel`/`decode3_kernel` for float and double on gfx90a, gfx942, gfx1100 — is `private_segment_fixed_size > 0` (register arrays demoted to scratch)? If so, C6/C4 become urgent.
2. Per-call breakdown (rocprof API trace) for 64³ and 512³ fields in all three modes: how much of `arctoZFPCompress/Decompress` wall time is `device_init`, hipMalloc/hipFree, memset, pageable memcpy vs kernels — quantifies H1/H2/D4 before kernel work.
3. L2 request amplification of the encoder's word writes and the decoder's word reads (`TCC_REQ` vs `FETCH/WRITE_SIZE`) to size C9/D2.
4. Effect of `__launch_bounds__(128,{2,3,4})` and WG size on encode3/decode3 (occupancy vs spills) on each arch.
5. Cooperative launch availability/cost (`hipDeviceAttributeCooperativeLaunch`, `grid.sync()` latency) on the deployed ROCm for gfx1100 in particular; whether `hipLaunchCooperativeKernel` succeeds for all tile tiers (`variable.h:332-339`).
6. ROCm version in deployment: `hipMallocAsync`/mem-pool support (≥5.2), and the measured cost of `hipFree` (device sync) and `hipHostMalloc`.
7. Non-integer fixed rates (word sharing → 64-bit atomics on every slot edge) vs integer rates: correctness on AMD (coarse-grained memory) and cost delta.
8. Unaligned `dwordx4` behaviour/cost when `nx%4≠0` (C1/D1) — hardware unaligned path vs scalar fallback.
9. wave32 vs wave64 (`-mwavefrontsize64`) for these kernels on gfx1100; HIP default for gfx11 is wave32 and nothing in zfp depends on wave size.
10. Fixed-accuracy path: share of the 2120-bit-slot memset (≈1.03× input) and of the ~1.06×-input transient device allocation in total compress time (C3/H2).
11. Whether hipcc constant-folds `perm_3[i]` (`constants.h:47`, used at `encode.h:232`, `decode.h:169`) after full unroll or emits scalar-cache loads (cheap either way, but confirm there is no per-lane VMEM gather).
